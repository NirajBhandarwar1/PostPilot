## Problem Statement

The user wants AI hiring managers and recruiters to notice them on LinkedIn. PostPilot v0.3
already runs: it scouts trending AI-industry stories every 3 days (Google News x12 queries,
Hacker News front page, Reddit RSS, GitHub trending, Hugging Face trending), scores "heat",
uses a free open model (Groq gpt-oss-120b, fallbacks Cloudflare and OpenRouter) to pick 3
topics and write post ideas, saves them (email pending Gmail setup), and on a reply builds
experiment code plus a humanized post draft.

User verdict on the last runs: "better than previous but still need to improve". Observed
failures across four runs:
- Earlier runs pitched generic exercises or niche Hugging Face models instead of what the
  industry is talking about (fixed in v0.3 by news-weighted heat).
- The free model invents facts: which provider hosts which model, that a model is
  multimodal, that an Anthropic S-1 exists, links a demo for the wrong model.
- Outdated model names (GPT-4, Llama 3, Mixtral) leak in as face-off rivals (partly fixed:
  regex check plus one retry).
- Every idea is a one-off; nothing compounds into a recognizable series or into portfolio
  proof.

## What Makes This Cool

The radar is itself the proof. A person whose LinkedIn shows a weekly "AI Heat Index" chart
generated by a system they built, plus fast hands-on reactions to whatever just went viral,
reads as someone who builds AI systems, not someone who reposts AI news. Every post links to
something real.

## Constraints

- Free only: Groq free tier (about 8K tokens per minute, 1K requests per day), Cloudflare
  Workers AI, OpenRouter free models. No Claude or OpenAI API.
- Runs on a Windows laptop (i5, 16 GB RAM, no usable GPU); cloud hosting later.
- Never posts to LinkedIn automatically (User Agreement); the user copies and posts.
- Never fabricates results; anything not measured is a {{placeholder}}.
- User time: about 1 hour per build post, 10-20 minutes for light formats.

## Premises (all confirmed by the user)

1. Posts alone do not get you hired. Every post points to proof (repo, demo, or chart), and
   the LinkedIn headline and Featured section are set up to catch the traffic.
2. The hot topic is the hook; the user's real result is the content. PostPilot never
   produces a post that can be published without actually running or making the thing.
3. One system, four formats on rotation: weekly AI Heat Index (auto), first-to-try on spikes,
   weekly deep experiment, hot takes in between.
4. The current quality bottleneck is facts. PostPilot must verify that named models, APIs
   and links exist before pitching an idea.
5. PostPilot itself goes public on GitHub as the flagship portfolio project; the Heat Index
   is its visible output.

## Approaches Considered

### Approach A: Minimal fix
Fact verification plus a "proof" field on each idea, keep the 3-day email flow. Small and
fast, but still one format with no Heat Index and no spike alerts. Not chosen: leaves three
of the four formats the user wants unbuilt.

### Approach B: Content engine, staged (CHOSEN)
Daily radar with stored heat history, spike detection, weekly Heat Index chart, four format
lanes, fact verification, and a public experiments repo for every build.

### Approach C: Public Heat Index website
Ruled out for now: a site to maintain before the content loop works. Can sit on top of B's
heat history later.

## Recommended Approach

Approach B, in stages. Each stage ships something usable.

**Stage 0: Repo safety (before the first commit).** (R1-11)
- Keep the `HF_TOKEN` line in `.env` (it is the user's own token, confirmed 2026-10-20); the
  secret check protects it. Hugging Face lookups use the anonymous public API.
- `.gitignore` covering `.env`, `data/`, `.venv/` exists before `git init` (it already does).
- A `python -m postpilot precommit` check runs before every commit and push: it lists staged
  files and refuses if `.env` is staged or any staged file contains a key pattern
  (`sk-`, `gsk_`, `nvapi-`, `hf_`, `cfut_`). The user runs commit and push by hand.

**Stage 1: Trustworthy ideas (fact gate).**

*Claims the idea must declare.* Each idea gets a `claims` list. Every claim has a type, a
subject and the sentence it supports:
- `runs_model`: a model the user must call to do the build (face-off rivals, the model in a
  first-look, build-with-it or stress-test).
- `model_hosted`: "model M is available on provider P".
- `model_capability`: "model M does X" (e.g. image input).
- `event`: a company or news claim (funding, filing, lawsuit, launch date).
- `number`: a price, a benchmark score, a count.

*Claims PostPilot finds itself.* (R2-1) The model's own `claims` list is not trusted to be
complete. Before checking, PostPilot scans the idea's title, build plan, hooks and needs for
model mentions in three ways: (a) any id from the fetched catalogs or the Hugging Face trending
list, (b) the outdated-name pattern (GPT-3.5/4/4o, Llama 2/3, Mixtral, Claude 2/3, Gemini
1.5/2, PaLM, Falcon), and (c) a model-name pattern: a capitalised word directly followed by
a version number (e.g. "Qwen3.8-27B", "Gemini 4 Argon", "Llama 3"). Pattern (c) counts as a model mention only when the word before the version number is a
known model family: a family name taken from the fetched catalog ids and Hugging Face trending
ids (the part before the first digit), plus a fixed list (gpt, claude, gemini, llama, qwen,
deepseek, mistral, mixtral, grok, muse, phi, gemma, kimi, glm, nemotron, minicpm, flux, ltx).
Words such as Python, Windows, Stage, Step, Top, Next.js, Node, iOS, Android, Week, Day and
Part never count. Every mention not
already covered by a declared claim is added as a claim. It is a `runs_model` claim in lanes
that run models and a `mention` claim otherwise, and it is checked like the rest. 
Sentences in the title, build plan, hooks and why-hot that contain a digit, a currency or
percent sign, or one of these event words (raised, valuation, funding, filed, filing, lawsuit,
sued, banned, acquired, acquisition, launched, released, IPO) are also added as `event` or
`number` claims and checked like declared ones.
An outdated-name hit triggers the regeneration only in lanes that run models (see below).

In lanes that do not run models (hot take, data-take, claim-check, what-it-means, Heat
Index), an outdated name is not regenerated. It becomes a `mention` flagged "older model:
make sure the post presents it as older", because comparing against an older model can be
the point.

*How each type is checked.* (R1-2, R1-3)
- Model catalog: once per run, fetch `/models` from every configured free provider (Groq,
  Cloudflare, OpenRouter `:free` only). Normalize ids: lowercase, drop the vendor prefix
  (`openai/`, `@cf/...`), replace any run of non-alphanumerics with `-`. A model matches a
  catalog entry only when the normalized names are EQUAL after also stripping these suffixes:
  `-instruct`, `-chat`, `-versatile`, `-instant`, `-free`, `-preview`, `-latest`. There is no
  substring or partial matching, so "llama-3" never matches "llama-3-3-70b-versatile". (R2-2)
  The idea prompt lists the exact catalog ids, and lanes that run models must use one of
  them word for word.
- `runs_model` and `model_hosted`: must match an entry in the fetched free catalog of the
  named provider. Lanes that run models (face-off, first-look, build-with-it, stress-test)
  may only name models that pass this check. A model known only from the news is allowed
  only in lanes that do not run it (Heat Index, hot take, data-take, claim-check,
  what-it-means).
- `model_hosted` naming a provider PostPilot has no catalog for (AWS Bedrock, Vertex, Azure,
  Together, a vendor's own API): flagged unverified with a warning, never a reason to drop the
  idea, unless the lane runs that model. In that case a `runs_model` claim on a free catalog
  provider must also pass. (R2-6)
- `mention` (a model named in a lane that does not run it): passes if it is in a catalog, on
  Hugging Face, or in one of the topic's signal titles; otherwise flagged unverified.
- `model_capability`: for open models, check the Hugging Face repo with the anonymous API
  (`/api/models/{id}`): the repo must exist and its `pipeline_tag` must be compatible
  (image or video input needs an `image-*`, `*-to-text` with image, or `any-to-any` tag).
  For closed models there is nothing to check against, so the claim is flagged unverified.
- `event`: passes only if one of the topic's signal titles contains the claim's subject
  entity plus at least one other significant word of the claim. Otherwise it is
  flagged unverified.
- `number`: always flagged unverified unless the exact number appears in a signal title.

*Links.* (R1-5) There is no extra network fetch. A source URL stays attached to a topic
only if the URL or its signal title contains at least one of the topic's entity tokens
(normalized as above, at least 4 characters, ignoring a stop list: ai, model, models, open,
new, launch, the, and, for, with). For ideas naming a Hugging Face or GitHub repo, a demo or
repo link must contain that repo's name. Dropped links are removed with no replacement. If a
topic has no links left, the topic is excluded.

*What happens on a failure.* (R1-4)
- An idea with a failing `runs_model` or `model_hosted` claim is regenerated once, alone (one
  extra call of about 4K tokens, which goes through the existing 429 retry). If it still
  fails, it is dropped.
- Unverified claims (closed-model capability, events and numbers with no matching title)
  do not drop an idea. They are listed under "Check before you post" with a warning mark,
  both in the saved ideas file and in the email.
- A batch needs at least 2 passing ideas to be sent. Below that, it is sent with a "short
  batch" header and the failure reasons. With 0 ideas, nothing is sent: the failure is logged
  and the next scheduled run tries again.
- Fetch failures: the catalogs and Hugging Face results are cached in
  `data/catalog_cache.json` for 7 days, and a failed fetch uses the cache. With no cache,
  that provider's models are unverifiable: lanes that run models fail closed (the idea is
  dropped), and claims checked against Hugging Face fail open with a warning mark.

*Proof.* Each idea also gets a `proof` field: the exact artifact the post will link
(`experiments/<slug>/`, `takes/<slug>/chart.png`, `heat-index/<week>.png`).

**Stage 2: Heat history and spike alerts (first-to-try).**

*Daily radar.* One topic-finding call per day. Each topic is stored per day as: date,
topic_id, name, entities, raw heat, share, the source kinds it was seen in, and its URLs.

*Topic identity across days.* (R1-7) Topic-finding also returns `entities`, most specific
first (e.g. ["gemini 4 argon", "google"]). Normalization: lowercase, strip accents and
punctuation, collapse spaces, drop the stop list. A new topic matches a stored topic from the
last 14 days if their FIRST entities are equal, OR they share at least 2 URLs. If several
stored topics match, take the one with the most shared URLs, then the most recent. Stored
topics are never merged after the fact. A topic with no match is new.

*Daily share.* (R1-8) share = raw heat / sum of all topics' raw heat that day × 100. This
makes days comparable even when the number of sources changes.

*Spike rule.* (R1-6) Source kinds: News, Hacker News front page, Reddit, GitHub trending,
Hugging Face trending models. Let `prev` be the topic's highest share in the 3 days before.
- A topic spikes when today's share is at least 12 AND it is either new (no `prev`) and seen
  in at least 3 source kinds today, or today's share is at least 1.8 × `prev` and at least
  `prev` + 6.
- Warm-up: no alerts until the history has 3 days. Those days are only recorded.
- At most 1 spike email per day and 2 per week (the highest share wins). A topic that
  alerted cannot alert again for 7 days.
- The spike email carries one first-to-try idea, built through the Stage 1 gate. The lane
  follows how the spiking thing can be accessed (R2-3):
  1. It is in a free catalog: face-off or first-look, running it through the API.
  2. Otherwise, if there is a public demo (a Hugging Face Space or an official "try it" page
     among the topic's signal URLs, and its URL contains the model's name): "first-look via
     demo". The user tries it by hand in the browser and records the screen. This is a
     `uses_demo` claim, checked against the signal URLs, and there is no `runs_model` claim.
  3. Otherwise: claim-check or what-it-means (below), which do not run the new model.
  If the spike idea fails the gate, it is regenerated once on the next route down (1 to 2,
2 to 3). If route 3 also fails, the email is sent as a news-only alert (the topic, why it is
spiking and its links, with no idea). A news-only alert does not count toward the weekly cap of
2.
  A spike is never dropped just because the model is not in a free catalog. The email says
  which of these routes it took.

*Missed and late runs.* (R1-9) The loop checks every 10 minutes, and the radar runs once per
calendar day on the first tick of that day. If the laptop was off, the next start runs today
only (no backfill). Missed days are stored as gaps and count as 0 in weekly totals.

*Missed scheduled emails.* (R2-5) The Monday, Tuesday and Thursday emails each have a due
day. On the first tick on or after the due day, the email is sent if it has not gone out this
week, as long as its next due day has not arrived; once it has, the missed one is skipped and
logged. Each email goes out at most once per week. A late email keeps its content (for
example, the Tuesday batch sent on Thursday is still that week's batch).

*Free-tier budget.* (R1-9) Worst case per day: 1 topic call (about 7K tokens), 1 idea call on
idea days (about 6K), 1 spike idea (about 4K), up to 3 regenerations (about 4K each). That is
at most about 29K tokens and 10 requests per day. Groq's gpt-oss-120b free limits are 30
requests per minute, 1K per day, 8K tokens per minute and 200K tokens per day (Groq
rate-limits page, checked 19 Oct 2026). Calls are spaced by the existing 429 retry using
`retry-after`. Reddit: 4 subreddits per day at 7-second spacing, and throttling only reduces
signals. Google News: 12 queries per day.

**Stage 3: Weekly AI Heat Index.**
- Weekly heat = sum of a topic's daily share across the Monday-to-Sunday days present, with
  missed days counted as 0. The chart says "based on N/7 days". Ties are broken by the
  highest single-day share. (R1-8)
- It is generated on the first run on or after Monday for the previous week. If late, it
  still covers that week and is labelled with its dates.
- Published files live in `heat-index/<YYYY>-W<ww>.png` and `.csv` (date, topic_id, name,
  share) inside the repo, separate from the ignored `data/`. PostPilot writes the files and
  prints the git commands. The user commits and pushes after `precommit`. (R1-10)
- The draft post asks for the user's take on the top 3 only.

**Stage 4: Format lanes and the weekly schedule.** (R1-12, R1-13)

| Day | Email | Lane | User time |
|---|---|---|---|
| Monday | Heat Index chart + draft | Heat Index | about 15 min |
| Tuesday | 3 ideas; the user picks 1 as the week's deep experiment | face-off / first-look / build-with-it / stress-test / claim-check / data-take / what-it-means | 1-3 h |
| Thursday | 1 hot take | hot take | about 20 min |
| Any day | Spike alert (at most 2 a week, optional) | first-to-try | about 1 h |

- If the user builds a spike alert that week, the Thursday hot take is skipped.
- Weekly budget: about 2-4.5 h. The old 3-day cycle is replaced by this calendar.
- Deep experiment: built into `experiments/<date>-<slug>/` with a README (problem, setup,
  result table, decisions).
- Lane definitions (R2-4). Each lane names its data source and its proof:
  - face-off: the same input to 2-3 free-catalog models; it compares speed, cost or
    quality. Proof: `experiments/<slug>/` with the script and a result table.
  - first-look: one free-catalog model, or a public demo (spike route 2), on a relatable
    task. Proof: `experiments/<slug>/` (the script or the screen recording plus notes).
  - build-with-it: a small useful tool using a free-catalog model. Proof:
    `experiments/<slug>/`.
  - stress-test: inputs designed to break a free-catalog model. Proof:
    `experiments/<slug>/` with the failure cases.
  - claim-check: tests a claim quoted from a signal title, using free-catalog models or
    public data. Proof: `experiments/<slug>/`.
  - data-take: a chart built only from public data that needs no login: the heat history,
    GitHub stars (GitHub API), Hugging Face downloads and likes (HF API), and catalog
    presence. Prices count as unverified numbers. Proof: `takes/<slug>/` (chart PNG + CSV).
  - what-it-means: a short demo, using free-catalog models, of what the story changes for
    builders. Proof: `experiments/<slug>/`.
  The Tuesday batch draws from face-off, first-look, build-with-it, stress-test, claim-check,
  data-take and what-it-means. Spike alerts use the routes above.
- Hot take: one opinion plus one chart. The chart data comes only from the heat history
  (e.g. a topic's 14-day share versus its rivals), so nothing is invented. The chart and CSV
  go to `takes/<date>-<slug>/`, which is the artifact the post links.

**Stage 5: Feedback loop.** (R1-14)
- Capture: email reply syntax `2` (pick) or `2 rate 4 5 2` (pick idea 2 and rate all three
  ideas 1-5). The CLI does the same before Gmail is set up:
  `python -m postpilot pick <batch> <n> [--rate 4 5 2]`.
- Post stats: `python -m postpilot stats <batch> --impressions N --reactions N --comments N
  --profile-views N`.
- Baseline before the first post: `python -m postpilot baseline --profile-views N
  --followers N --recruiter-msgs N`.
- All of this is stored in SQLite tables `ratings`, `post_stats` and `baseline`. A weekly
  report ranks formats and topic kinds by engagement rate and by rating.

### R3-1 — completeness (blocking)

**Problem**

> Persisting from R2-1. The new 'Claims PostPilot finds itself' scan only looks for model mentions (catalog ids, the outdated-name pattern, a name-plus-version pattern). Event statements, numbers and provider/hosting statements that the model leaves out of its own `claims` list are still never checked. The invented 'Anthropic S-1' (a failure named in the Problem Statement) or an invented price or benchmark score would reach the email with no 'Check before you post' warning. The first success criterion and Premise 4 depend on every factual statement being checked.

**Remedy**

> Extend the scan to undeclared events, numbers and provider names: for example, any number or percentage in the idea text not already covered by a `number` claim becomes an unverified `number` claim; any company or provider name from a fixed list (or the topic's entities) in a sentence not covered by a claim becomes an `event` or `model_hosted` claim and is checked or flagged. Alternatively, state that every sentence of the hooks containing a number or a company name is listed under 'Check before you post' unless a claim covers it.

### R3-2 — completeness (blocking)

**Problem**

> Persisting from R2-3 (in part). The spike routes now cover models outside the free catalogs, but the document still does not say what happens when the spike idea itself fails the gate (for example a route 3 idea is regenerated and still fails, or a route 1 idea's rival model fails), nor whether such a failed spike uses up the daily or weekly alert cap or starts the topic's 7-day cooldown. The original remedy asked for both.

**Remedy**

> State the outcome when no spike idea passes (send the alert without an idea, try the next route, or skip), and state whether a sent or skipped spike counts against the 1/day and 2/week caps and starts the 7-day cooldown.

### R3-3 — feasibility (blocking)

**Problem**

> Pattern (c) (a capitalised word followed by a version number) also matches ordinary text such as 'Python 3.12', 'Windows 11', 'Stage 1', 'Top 3', 'Step 2', 'Next.js 15' or 'GPT-5'-style product names that are not models. In lanes that run models, every such hit becomes a `runs_model` claim that cannot match a catalog id, so the idea is regenerated and then dropped. Many valid build ideas would be dropped and batches would fall below the 2-idea minimum.

**Remedy**

> Restrict pattern (c) to words that look like model families (a maintained list of model family names, or words that appear in the fetched catalogs or Hugging Face trending ids), or add a stop list for common software and ordinal words. In lanes that run models, treat a pattern-(c) hit that is not in the idea's run list as a `mention` claim rather than a `runs_model` claim.

**Remedy**
